# Three.js PDF hall importer and Hall Layout integration

Open **Select Hall → Import a floor plan** and choose a PDF. Both file selection and drag/drop open `/planner/editor?import=pdf`: the PDF appears in the existing main planner's `Scene3dComponent` renderer, scene and canvas. Hall Layout import controls appear in its sidebar. No separate PDF canvas or import page is opened. Older `/planner/pdf?document=…` links redirect to this route while retaining the local document. The main planner's **Import PDF plan** buttons use the same local flow. DXF and image imports keep their existing routes.

PDF processing stays in the browser. A reviewed, calibrated hall boundary can now be saved through the existing planner API and opened in the main 3D planner with a local PDF crop underneath. Automatic stall classification, server storage of the original PDF/review objects, full document-content editing, OCR and automatic legend matching remain separate work.

## Use

1. Open a PDF (maximum 25 MB). It is parsed locally with PDF.js; no PDF upload, LLM, Gemini or external processing service is used.
2. Select a page. **Top view** supports pan/zoom; **3D orbit** tilts the complete drawing. The original is rendered as a bounded overview texture plus a fresh visible-area texture after zoom/pan. **2D reference** remains available for comparison or if WebGL is unavailable. Both views use the same editable geometry and source coordinates.
3. Use **Calibrate scale** to mark two points and enter a known distance in metres. Exact page coordinates can also be entered. A page or individual hall can have its own calibration. Assign objects to a hall to inherit its scale. Check a different dimension with **Measure** before relying on dimensions.
4. Select a simple closed source path, or **Trace outline**. Diagonal polygons are supported. Curved, compound and clipped paths remain in the original drawing; they are not silently flattened into polygons. Hidden optional-content layers are excluded from selection.
5. Name and classify the outline. Names, hall grouping, symbol meanings and heights are never inferred from this one example PDF. Trace a legend sample as a `legend` object, then explicitly associate a `symbol` with it. Review flags and missing-property reports remain separate.
6. Move in calibrated metres or edit vertices. There is no automatic half-metre snapping or auto-fit. Source coordinates remain unchanged; Undo/Redo restores object edits. Every polygon with an explicit height and applicable calibration appears as an extrusion in Three.js; all others remain flat. These are geometry previews, not inferred building construction. The full-page scene retains PDF proportions, including independently scaled regions; only a calibrated hall imported into the main planner is expressed in shared real-world metres.
7. **Save locally** retains the exact PDF bytes, hash, objects and calibrations in IndexedDB. Reopening the document verifies the original PDF hash. **Download backup** saves a portable `.pdfplan` file containing metadata and the original PDF; **Open backup** checks its schema, associations and hash, and imports a separate copy. **Download report** exports review data, not a replacement PDF or portable project.
8. Select a hall, confirm **I reviewed this outline and its meaning**, then choose **Save hall & open planner**. Only the selected hall boundary is sent as JSON to your planner's `/api/halls`; no PDF bytes or image upload is sent. The API must return unchanged geometry before the PDF reference is attached. Identical reviewed imports reuse their linked master hall; changed snapshots can create another hall. Repeat for separate halls or pages.
9. **Start stall layout** switches the existing planner from PDF import controls to its usual stall controls using the selected reviewed, calibrated hall. The renderer, scene and canvas stay mounted; the source page view becomes the calibrated hall crop. If a required input is missing, the action focuses the boundary, object type, scale or review step. Reopening a PDF with one hall on the current page selects that hall; multiple halls require an explicit choice. This local transition works without a backend and does not create a server hall. **Preview in main planner** is an equivalent secondary action. Reloading restores the reviewed hall from the local PDF project, not unsaved stall edits made inside the planner.

The planner shows a bounded 2048-pixel PDF crop of the hall's bounding box, with a blue reviewed-boundary outline. It is a floor reference, not an editable PDF or a claim of unlimited zoom fidelity. The original full page, labels and legends remain accessible through **Open original PDF / import another hall**. Toggle **Show original drawing** to compare with the planner floor. Imported PDF halls do not receive the old renderer's guessed 1.5 m boundary walls. Other PDF objects stay in the review workspace: no stalls, facilities, restrictions or heights are silently invented.

Local reference bindings snapshot the source crop, scale, page, PDF hash and saved hall geometry. Changed server geometry disables an old overlay. Exact saved-layout copies can reuse a matching binding; conflicting source mappings are flagged instead of guessed. Bindings are browser-local and are not included in portable PDF project backups; restoring a backup on another browser requires linking/importing its hall again. Shared/exhibitor views do not yet carry this reference.

Original view shows only the source PDF. Compare shows original content and editable overlays, including the original position of a selected outline. Edited objects hides the original drawing: it does not erase source marks or claim complete WYSIWYG PDF editing.

Local drafts belong to the browser profile and app origin. Clearing site data loses them, so keep portable backups. No service worker is added: offline operation assumes the app is served locally, or its application assets are already available. The existing app-wide Google Fonts link is unchanged; its system-font fallback works without internet. PDF workers, CMaps and standard PDF fonts are bundled locally.

## Representation and limits

### Prepared local review links

For a prepared review package, run `node scripts/serve-pdf-preview.cjs <prepared.pdfplan> <preview-key>` alongside the frontend on port 4321, then open `/planner/editor?pdfPreview=<preview-key>`. The package server binds only to loopback port 4322 and serves one explicitly named file. Packages belong outside public/assets (for example, the ignored `node_modules/.cache` directory); PDF bytes are not included in a production build. This entry point is disabled in production and on non-loopback app origins. Backups receive the same schema/hash checks as manual backup import and a stable browser-local ID.

The link opens a read-only overview of all prepared halls in their original PDF positions. Hall buttons open the normal Three.js stall editor without re-uploading, retracing or changing canvas. The overview rectangle is only a viewing window; it is not inserted into the hall list or used for stall placement. All halls in an overview must share one page and scale. Review flags and scales come from the prepared package, not automatic detection. Preview stalls remain while switching halls but reset on reload; server Save/Publish is hidden in this mode. The normal import/save workflow is unchanged.

The supplied drawing's local Hall 8/9/10 package follows the PDF's brown floor-region outlines, including Hall 8's diagonal edge. Its scale uses ten consecutive intervals of the explicitly labelled 1 m grid (page x=1335.33 to 1423.62). This is a manually prepared review package; individual dimension annotations and semantic restrictions still need review. Heights remain unknown. `PDF_LOCAL_PREVIEW=<preview-key>` enables `e2e/pdf-prepared-preview.spec.ts`, which checks fresh-browser loading, all three halls, retained polygon vertices, manual stalls in each hall, reload and desktop/mobile layout.

Prepared previews now default to clean floor meshes: halls in light grey and reviewed foyers in blue, with only names and perimeter lines. “Show original drawing” restores the unchanged PDF crop, including all its grid, dimensions and symbols. It is a visibility toggle, not a PDF filter. The clean view does not reconstruct columns, doors, services or walls; the UI says these remain in the source. The normal PDF hall workflow retains its original-drawing default.

The local package includes manually traced gross footprints of Foyers C, B and A (including entry vestibules), respectively adjoining Hall 10, Halls 10/9, and Halls 9/8. C excludes the stair run x=815.19..824.79, y=973.81..992.05 and steps inward at y=1291.60. B follows the brown step around its stair enclosure at x=1288.14, y=1183.30. A starts below the toilet/stair wall at y=1238.65. These footprints are contextual floor areas, not certified net usable areas; internal columns and partitions remain in the original drawing. Foyers do not enter the selectable hall list or expand stall placement. `adjacentHallIds` preserves reviewed shared connections in backups; broken references, unreviewed foyers or inconsistent scales fail explicitly. Changing a connected hall's type/calibration or deleting it invalidates dependent review.

All floor regions and the expanded PDF reference use the selected hall's unchanged centre origin. Only the camera bounds and source crop expand for adjoining foyers; the crop has an explicit world offset. The overview draws six real polygons rather than a filled rectangle spanning empty space. No height is inferred.

Run `PDF_PREPARED_PACKAGE=<private.pdfplan>` with `e2e/pdf-floor-geometry.spec.ts` for the actual package check. The updated browser regression covers clean/source toggles, foyer framing and rejection of stall moves into foyers, but was not run in this update: browser access was rejected by the browser security policy. Desktop/mobile visual QA and live interaction confirmation remain pending for this change.

- Source geometry uses the PDF.js scale-1 viewport. Page reports include PDF rotation, UserUnit and the PDF-to-viewport matrix. A viewport unit is not a CAD metre.
- Real-world coordinates derive from explicit two-point calibration. This does not correct perspective distortion in scans or establish physical site measurements.
- Immutable `sourcePoints` are separate from editable `points`. Objects retain their page, source path reference where available, review state, region and legend associations.
- Curve control points are retained for source selection/highlighting; curved, clipped and compound paths cannot be converted directly to editable polygons. The original PDF is authoritative for appearance.
- Three.js pointer tools use ray/plane intersections in both top and tilted views, and ignore drags/multitouch as drawing clicks. Curved, clipped or compound source selections show a labelled bounding-box highlight in Three.js; 2D reference can display their source path highlight. The rendered original is preserved in both views.
- Reports include text runs and unsupported content counts. Source paths are geometry candidates, not a verified inventory of stalls. Text outlines, image content and ambiguous symbols require review; OCR is not enabled.
- Extraction yields periodically and reports its path-processing resource limit. PDF.js parsing/rendering uses its worker, but geometry post-processing remains in the browser. This is not yet a production job queue with server-enforced memory limits.
- Editable outlines allow 3–500 finite, non-self-intersecting vertices. Known missing heights remain null. 3D is a selected-object geometry preview, not a reconstructed building.
- Clipping, transparency, fonts, line styles and other original appearance are handled by PDF.js rendering, not reconstructed from the simplified geometry adapter. Pixel identity across different PDF engines is not asserted.

## Implementation

`src/app/planner/pdf-workspace/` contains the PDF adapter and tile renderer, coordinate/calibration model, IndexedDB persistence, portable backup validator, Angular review UI, optional Three.js object preview and hall adapter. `PdfImportNavigation` passes selected files in memory. `preparePdfHall` maps viewport X/Y to centred planner X/Z metres without snapping or simplifying vertices. `PdfHallReferenceComponent` verifies local PDF bytes and loads a bounded texture into `Scene3dComponent`. IndexedDB version 2 adds hall reference bindings while preserving existing version 1 documents. The backend API contract is unchanged.

`PdfThreeSceneComponent` owns the import camera, controls, bounded PDF textures and editable object meshes. In the planner it borrows the existing renderer/scene through `PdfDrawingSurface`; it neither creates a second WebGL canvas nor disposes the planner renderer. The planner temporarily suspends stall pointer handlers and uses the import camera. Import teardown removes its layers, camera and listeners and returns control to normal stall editing. It shares the PDF reader with the 2D reference, disposes its own textures/geometries, and ignores obsolete async tile results. Positive PDF Y maps to positive scene Z. Extrusion depth is `confirmedHeightMetres / objectMetresPerUnit`; PDF units are never silently treated as metres.

## Verification

Run `npm run build` and `npx playwright test e2e/pdf-workspace.spec.ts`. Set `PW_PORT` to an unused local port if needed. The app's existing production font-inlining step requires network access to Google Fonts at build time.

The Playwright suite creates its own small PDF with text, a transformed diagonal polygon, a cubic curve, clipping and a second rotated page. It exercises calibration, unknown properties, selection, manual tracing, editing, undo, reload, source-byte integrity, portable backup validation, optional 3D preview, invalid files and mobile overflow.

For the supplied drawing, set `PDF_REFERENCE_FILE` to the local `8-9-10.pdf` path. The customer file is never copied into the repository. The integration test verifies the source hash, grid text, Hall 8/Hall 9 labels, extraction counts, exact-coordinate tracing of two reviewed grid-region samples, calibration persistence and portable backup reopening. Those samples are test inputs, not production hall templates or claims about complete hall boundaries.

Measured on the supplied file: 1 page, 75,188 paths, 459 PDF.js text runs and 23 layers. Text-run counts depend on the extraction engine and are not label counts. The original SHA-256 is `66853f7dea94ff21bc05a0fda31af9de38cbfaa9829d561502d479f958724127`.

The `pdf-workspace.spec.ts` integration suite also exercises Hall Layout upload → local PDF review → hall API write → main planner, repeated import without duplicate writes, reference reload/toggle, exact polygon transfer, no fabricated walls/stalls and a backend-failure/local-preview path. Those API writes are intercepted. A successful hall save refreshes the server list so a previously empty list does not leave an incorrect "Offline sample" message.

`pdf-live-validation.spec.ts` is a separate opt-in test with real API/database writes. Run only against a disposable local planner API/database with `PDF_LIVE_VALIDATION=isolated-local-db`, `PDF_REFERENCE_FILE` pointing to the supplied drawing, and `PW_PORT` set to the running frontend. It imports a manually reviewed Hall 9 grid-region sample, saves/reloads the hall, verifies the same Three.js canvas and reference pixels, then explicitly adds and saves a 3 × 3 × 2.5 m stall. It writes measured evidence to `test-results/pdf-live-validation.json` and screenshots beside it. No request interception is used.

The local live run on 2026-10-08 used a temporary snapshot of the compatible backend `main` source with a separate PostgreSQL database (`codex_pdf_live_20261008`). The checked-out backend feature branch did not expose the required hall/layout API; this test server is not a permanent backend-branch migration. Measured results: hall and layout saves returned 201, subsequent reads returned 200, the 33.51334182190605 × 27.023597309491517 m sample boundary had zero numeric error relative to its typed calibration, and the 2048 × 1652 planner texture matched the source crop rendered by the same PDF.js engine. No walls or stalls were created automatically. The explicit manual stall persisted. All writes were JSON; no PDF was uploaded. These checks establish rendering/coordinate transfer and persistence for this sample, not automatic recognition of the complete Hall 9 or physical accuracy of its dimensions.

Three.js checks exercise the default full-page import, ray-picked tracing in a tilted camera (<0.0001 page-unit pointer error on the synthetic fixture), measured distances, scale-gated height extrusion, zoom-detail refresh, switching to/from 2D, and page isolation. Pointer precision is distinct from exact typed-coordinate calibration; neither certifies the drawing's real-world dimensions.

Independent visual-difference benchmarking, real-world dimension certification, broad multi-document extraction accuracy and automatic stall/legend mapping are not completed by these tests.
